VM on an Ubuntu server

You can do this with raw QEMU, but you'd have to write a systemd unit, port forwarding and autostart yourself. I'd use Incus on the server: it's an apt package, it starts VMs at boot, and it's the same setup we just tested locally.

1. On the server, once:
sudo apt install incus
sudo usermod -aG incus-admin $USER && newgrp incus-admin
incus admin init --minimal
incus network get incusbr0 ipv4.address        # e.g. 10.42.17.1/24 → the VM can use 10.42.17.10

2. Settings: copy user-data.yaml to the server as varsis.yaml and edit it:
- DOMAIN=music.example.com
- ADMIN_EMAILS=you@…
- the SMTP_* values for your mail provider
- MAILPIT=false and SITE empty (both are already like that)
                                                                                                      3. Point DNS: set the domain's A record to the server's public IP.

4. Create the VM with a fixed internal IP, so port forwarding can always find it. Use the subnet from
step 1:
incus launch images:ubuntu/24.04/cloud varsis --vm \
  -c limits.cpu=2 -c limits.memory=2GiB -d root,size=30GiB \
  -d eth0,ipv4.address=10.42.17.10 \
  -c cloud-init.user-data="$(cat varsis.yaml)" \                                                         -c boot.autostart=true
                                                                               5. Forward the server's ports 80/443 to the VM. Let's Encrypt needs both. Replace <server-ip> with the
server's public IP:                                                            incus config device add varsis http  proxy nat=true listen=tcp:<server-ip>:80
connect=tcp:10.42.17.10:80
incus config device add varsis https proxy nat=true listen=tcp:<server-ip>:443
connect=tcp:10.42.17.10:443
If ufw runs on the server, also allow 80/443 there, plus the incusbr0 rules we needed locally.

6. Watch the setup. It ends with [varsis-setup] done: https://music.example.com:                 incus exec varsis -- tail -f /var/log/cloud-init-output.log                                   
I haven't tested steps 4–5 (fixed IP and port forwarding), because they need a public server and
domain. The setup inside the VM is the same as in the local tests, and only the Let's Encrypt      certificate there is untested.

If you'd rather use raw QEMU on the server, I can write a production version of run-qemu.sh with a
systemd unit instead. The cloud-init file stays the same either way.
